# Windows sandbox on macOS (Apple Silicon)

For repeated verification of Windows PowerShell 5.1 and PowerShell 7, use a licensed Windows 11 ARM64 VM on the Mac: the existing UTM guest is the lowest-friction choice, and UTM’s guest agent or Windows OpenSSH/WinRM can provide host-driven runs. Windows 11 ARM64 contains Windows PowerShell 5.1; install PowerShell 7 alongside it and test both executables. [Microsoft documents PowerShell 7 as side-by-side with Windows PowerShell](https://learn.microsoft.com/en-us/powershell/scripting/install/migrating-from-windows-powershell-51-to-powershell-7), and [UTM’s Windows guide](https://docs.getutm.app/guides/windows/) documents Windows 11 ARM64 virtualization on Apple silicon. A clean baseline snapshot plus restore (or UTM disposable start) makes runs repeatable; neither a Windows compatibility layer nor a Linux container is a substitute for the Windows OS and process environment. [UTM snapshots](https://docs.getutm.app/advanced/snapshots/) · [Wine overview](https://www.winehq.org/about) · [Microsoft Windows containers overview](https://learn.microsoft.com/en-us/virtualization/windowscontainers/about/)

## Local virtualization options

### UTM (recommended for the existing VM)

UTM’s Windows 11 guide directs Apple-silicon users to an ARM64 installer and the **Virtualize** path; it says a valid Microsoft Windows license is required. UTM’s free download is also distributed from its [official GitHub releases](https://github.com/utmapp/UTM/releases); the project’s [App Store listing](https://apps.apple.com/app/utm-virtual-machines/id1538878817) is a separately paid distribution. [UTM Windows 11 guide](https://docs.getutm.app/guides/windows/)

UTM uses QEMU for the Windows VM. CPU virtualization of an ARM64 guest is a better fit than emulating x86_64 Windows on an ARM Mac, but graphics are a distinct limitation: UTM describes Windows 11 DirectX acceleration as experimental and cautions about instability/limited compatibility. For this PowerShell/process test, use the normal display driver unless GUI/3D performance matters. [UTM Windows graphics notes](https://docs.getutm.app/guest-support/windows/) · [UTM QEMU settings](https://docs.getutm.app/settings-qemu/qemu/)

UTM’s scripting interface is more capable than just boot control: `utmctl` supports VM lifecycle, disposable start, clone, file push/pull, IP lookup, and `exec` of an application inside the guest **when the guest agent is installed**. `exec` is not a generic SSH replacement, and the guest agent requirement matters. The CLI wraps UTM’s AppleScript bridge; command syntax should be checked with the installed version’s `utmctl help <command>`. [UTM scripting and command list](https://docs.getutm.app/scripting/scripting/)

UTM headless mode means no UTM display window; its setup requires removing display devices and the app must remain open. Establish and test remote access before removing the display. For a GUI-assisted test, keep the display attached and close/minimize the window instead. [UTM headless mode](https://docs.getutm.app/advanced/headless/)

### Parallels Desktop

Parallels documents installing Windows 11 on Apple silicon and provides a 14-day Desktop trial. The Parallels trial does not activate Windows; Windows requires its own license. Microsoft’s Apple-silicon guidance identifies Parallels Desktop as an authorized solution for Windows 11 Pro/Enterprise VM scenarios on supported Apple silicon Macs. [Parallels install](https://kb.parallels.com/en/125375) · [Parallels trial](https://kb.parallels.com/en/124227) · [Microsoft Apple-silicon Windows guidance](https://support.microsoft.com/en-us/windows/experience/platform-variants/options-for-using-windows-11-with-mac-computers-with-apple-m1-m2-and-m3-chips)

Parallels has `prlctl` VM management and documents headless mode. The documented headless approach concerns running the VM without its graphical window; configure guest SSH/RDP or another guest-side remote method for interaction. Check `prlctl` and edition requirements (the CLI is documented for Pro/Business) before assuming an unattended automation setup is available on a given edition. [Headless mode](https://kb.parallels.com/en/123298) · [CLI edition support](https://kb.parallels.com/eu/128842/)

### Oracle VirtualBox

Correction to the old assumption that VirtualBox cannot run ARM guests on Apple Silicon: Oracle’s **7.2** manual lists macOS/Arm hosts and Windows 11/Arm guests on Arm hosts, and Oracle distributes a macOS Arm64 host installer. Use 7.2 or later; do not generalize this support to older releases. The manual documents `VBoxHeadless`, `VBoxManage`, snapshots, cloning, and unattended guest-install features. Oracle warns that Arm VM saved states from 7.1 are incompatible with 7.2, so shut down before upgrading. [Oracle VirtualBox 7.2 user guide](https://download.virtualbox.org/virtualbox/7.2.0/UserManual.pdf) · [Oracle downloads](https://www.virtualbox.org/wiki/Downloads)

The VirtualBox base package is GPL-licensed, while its Extension Pack has its own license/terms; do not assume Extension Pack features are covered by the base package license. Windows licensing remains separate. [VirtualBox licensing section in the manual](https://download.virtualbox.org/virtualbox/7.2.0/UserManual.pdf)

### QEMU directly

UTM wraps QEMU. A direct QEMU setup on macOS can use `qemu-system-aarch64`; QEMU documents `hvf` (Apple’s Hypervisor.framework accelerator) on macOS Arm hosts and supports CLI-based system emulation. This is a low-level route: selecting a Windows-compatible machine, UEFI firmware, virtual storage/network/display, and guest drivers is part of the configuration, not solved by the accelerator flag alone. QEMU’s manual identifies QEMU as GPLv2; that does not license Windows. [QEMU system intro](https://www.qemu.org/docs/master/system/introduction.html) · [QEMU Arm target](https://www.qemu.org/docs/master/system/target-arm) · [QEMU license](https://www.qemu.org/docs/master/system/)

### Apple Virtualization.framework

Apple’s framework documentation and sample flows explicitly cover Linux and macOS virtual machines; it does not document a Windows boot path. Therefore treat Windows guest support through this framework as **not officially established**, rather than assuming that Apple’s separate low-level Hypervisor framework is itself a Windows VM product. [Apple Virtualization](https://developer.apple.com/documentation/virtualization) · [Linux VM sample](https://developer.apple.com/documentation/virtualization/virtualize-linux-on-a-mac) · [Hypervisor framework](https://developer.apple.com/documentation/hypervisor)

### Why Wine, CrossOver, and Docker are not substitutes

Wine describes itself as a compatibility layer for Windows applications, and CrossOver translates Windows application commands for macOS/Linux rather than requiring a Windows installation. They may run some applications, but they do not provide a real Windows 11 guest in which the built-in Windows PowerShell 5.1 and Windows-specific process environment can be verified. [Wine](https://www.winehq.org/about) · [CrossOver](https://www.codeweavers.com/crossover/)

Microsoft’s Windows container documentation requires a compatible Windows container host and version match. Docker Desktop on macOS provides a Linux container environment, not a Windows host kernel; it cannot be used to launch a Windows container directly as a local Mac container. [Windows container host compatibility](https://learn.microsoft.com/en-us/troubleshoot/windows-server/containers/support-for-windows-containers-docker-on-premises-scenarios) · [Docker Desktop Mac install requirements](https://docs.docker.com/desktop/setup/install/mac-install/)

## Windows 11 ARM64 image source

Use Microsoft’s official [Windows 11 Arm64 ISO download page](https://www.microsoft.com/en-us/software-download/windows11arm64). Microsoft’s [Windows Arm ISO guidance](https://learn.microsoft.com/en-us/windows/arm/iso) explicitly includes creating an Arm64 VM on an Apple silicon Mac. The regular retail download path therefore is **not x64-only**: Microsoft has a separate ARM64 retail ISO page as well as the usual x64 page. The ISO is installation media, not a Windows license; follow the applicable Windows edition/license terms. [Microsoft Windows 11 Arm64](https://www.microsoft.com/en-us/software-download/windows11arm64) · [Windows 11 x64 download](https://www.microsoft.com/en-us/software-download/windows11)

The separate [Windows Insider Preview ARM64 download page](https://www.microsoft.com/en-us/software-download/windowsinsiderpreviewARM64) is for Insider Preview builds and requires Insider access/sign-in; use it only when testing a preview channel is intentional. The regular ARM64 download is the release-image path, so a preview ISO is not required for an ARM Mac VM. [Microsoft Insider ARM64 page](https://www.microsoft.com/en-us/software-download/windowsinsiderpreviewARM64)

## Provisioning a repeatable UTM box

Recommended pattern for the existing UTM Windows 11 ARM64 VM:

1. **Preserve a clean baseline.** Install Windows updates, UTM guest tools, Windows PowerShell 5.1 (already part of Windows), PowerShell 7, Node.js and the test harness. Verify the intended `powershell.exe` and `pwsh.exe` paths and launch both once. Windows PowerShell 5.1 and PowerShell 7 can coexist; PowerShell 7 is separately installed. [PowerShell migration/side-by-side guidance](https://learn.microsoft.com/en-us/powershell/scripting/install/migrating-from-windows-powershell-51-to-powershell-7) · [PowerShell install on Windows](https://learn.microsoft.com/en-us/powershell/scripting/install/install-powershell-on-windows)
2. **Automate Windows setup and first-logon provisioning.** Windows Setup supports an `Autounattend.xml` answer file on removable media. Use Windows System Image Manager against the chosen Windows image to build/validate it; put it at the root of attached setup media. For a first-logon setup script, configure `Microsoft-Windows-Shell-Setup\FirstLogonCommands` in the `oobeSystem` pass to invoke one script that installs/configures remaining tools and the harness. First-logon commands run after the first user sign-in; they are not an unattended, pre-login service. Run dependent setup steps in one script rather than multiple first-logon commands because Microsoft documents concurrency behavior for those commands. [Windows Setup automation overview](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/windows-setup-automation-overview?view=windows-11) · [Answer files](https://learn.microsoft.com/en-us/windows-hardware/customize/desktop/wsim/answer-files-overview) · [FirstLogonCommands](https://learn.microsoft.com/en-us/windows-hardware/customize/desktop/unattend/microsoft-windows-shell-setup-firstlogoncommands)
   
   In that script, install PowerShell 7 with `winget install --id Microsoft.PowerShell --source winget`, then install the Node test harness. Run this in the first-logon user context and confirm WinGet is registered there: Microsoft notes it may not be available immediately after a user’s first sign-in. [PowerShell installation](https://learn.microsoft.com/en-us/powershell/scripting/install/install-powershell-on-windows) · [WinGet availability](https://learn.microsoft.com/en-us/windows/package-manager/winget/)
3. **Choose a host-driven run channel.** Easiest UTM-native route: install/enable UTM’s Windows guest agent/tools, then use `utmctl exec` (and file push/pull if needed); UTM explicitly requires the guest agent for these commands. For a standard network route, enable Windows OpenSSH Server and use SSH from macOS; Microsoft documents OpenSSH Server on Windows 11 and automatic startup/firewall configuration. WinRM is another option via elevated `Enable-PSRemoting`, with network profile/firewall/authentication configured for the VM’s isolated network. UTM does not turn `utmctl` into a PowerShell command prompt: it starts a guest application; the guest process should run the requested PowerShell test command itself. [UTM CLI docs](https://docs.getutm.app/scripting/scripting/) · [OpenSSH Server setup](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_install_firstuse?pivots=windows-11) · [Enable-PSRemoting](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/enable-psremoting?view=powershell-5.1)
4. **Run both engines against the same test inputs.** Invoke `powershell.exe -NoProfile -NoLogo -Command ...` and `pwsh.exe -NoProfile -NoLogo -Command ...`; assert child exit status and capture stdout/stderr separately. If the test is meant to verify a Node process directly spawning the Windows process, run Node **inside the Windows guest**; a Mac-side SSH/agent run tests a remote transport boundary as well. Node child-process pipes provide Buffer chunks by default for `spawn`; encoding is not carried in a Buffer, so set/verify the expected PowerShell output encoding before decoding or compare raw buffers. `$OutputEncoding` controls text piped *to native commands*, not a blanket stdout encoding setting. [Node child_process](https://nodejs.org/api/child_process.html) · [PowerShell preference variables](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_preference_variables?view=powershell-7.5)
5. **Reset after a known-good baseline.** Use `utmctl snapshot create "Windows 11" --name "Clean test baseline"`, inspect with `utmctl snapshot list`, and restore with `utmctl snapshot restore "Windows 11" --snapshot "Clean test baseline"` (replace the name with the VM’s exact registered name). UTM documents these operations; a restore rolls back current changes. Snapshots exclude removable/read-only/external drives, so keep test inputs and any state that must survive restore outside the guest disk or in a separately managed location. [UTM snapshot commands](https://docs.getutm.app/scripting/scripting/) · [Snapshot semantics/limits](https://docs.getutm.app/advanced/snapshots/)
6. **Keep a separate backup/export.** UTM’s GUI can export the VM and data; snapshots are rollback points, not an independent backup. Shut Windows down before making a portable export. UTM’s CLI documentation lists snapshot operations but does not document a `utmctl` export/import command; use the GUI export/import workflow or documented AppleScript capabilities rather than assuming a CLI subcommand exists. [UTM VM actions](https://docs.getutm.app/basics/actions/) · [UTM scripting](https://docs.getutm.app/scripting/scripting/)

For unattended provisioning, test the answer file on a clone before replacing the working VM. Protect answer files containing credentials; avoid AutoLogon unless a setup action requires an interactive user session. Microsoft warns that automatic logon exposes the account to anyone with access to the machine. [Microsoft AutoLogon security note](https://learn.microsoft.com/en-us/troubleshoot/windows-server/user-profiles-and-logon/turn-on-automatic-logon)

## Cloud alternatives

- **GitHub Actions:** hosted Windows has x64 Windows Server labels and also Windows 11 ARM64 labels (`windows-11-arm`, `windows-11-vs2026-arm`) in GitHub’s current runner list. Choose explicitly: an x64 runner is not an ARM64 substitute, while the ARM label is useful for a cloud ARM run. Hosted images are disposable jobs and can run the same PowerShell/Node test harness after setup. Check current image availability, billing and tool preinstalls in GitHub’s runner reference. GitHub also documents Windows ARM64 **self-hosted runners**, currently marked public preview; jobs can target `[self-hosted, windows, ARM64]`. [GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) · [Self-hosted runner support](https://docs.github.com/en/actions/reference/runners/self-hosted-runners) · [Workflow labels](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/use-in-a-workflow)
- **Windows 365:** a licensed, Microsoft-provisioned Cloud PC is a persistent remote Windows desktop; useful when a managed remote interactive environment is wanted, not the cheapest transient per-test loop. [Windows 365 overview](https://learn.microsoft.com/en-us/windows-365/enterprise/overview)
- **Azure VM:** create and automate a Windows VM from an Azure image; useful when you need a remote machine you control. **Unconfirmed:** Windows ARM64 guest availability for the relevant Azure VM/image combination was not established by the primary source checked; do not assume it provides parity with the local ARM64 VM. [Azure Windows VM overview](https://learn.microsoft.com/en-us/azure/virtual-machines/windows/overview)

Architecture matters for interpretation: GitHub `windows-2025` / `windows-2022` runner labels are x64, whereas the local UTM Windows guest is ARM64; GitHub additionally lists Windows 11 ARM64 runner labels. [GitHub runner architecture table](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) Pure PowerShell logic may behave identically across architectures, but native executable/module dependencies, architecture-sensitive paths, and OS-specific behavior should be tested on the target architecture rather than inferred from an x64 result. [Inference based on the runner architecture distinction; PowerShell 7 supports ARM64 Windows](https://learn.microsoft.com/en-us/powershell/scripting/install/install-powershell-on-windows)

## Limits

- Microsoft, Parallels, Oracle and UTM documentation can change by product version, edition, Windows build, and licensing terms; use the linked current vendor page and license presented for the exact build you install.
- **Unconfirmed:** Apple’s public Virtualization.framework documentation describes Linux/macOS guests but does not explicitly state whether Windows is supported; this document reports that support is not established by those docs, not a universal prohibition.
- **Unconfirmed:** UTM’s scripting docs do not promise a cross-platform command-line quoting or binary-stdout transport contract for `utmctl exec`. For exact raw byte assertions, execute Node and PowerShell inside the Windows guest, or validate any host-driven transport separately. `utmctl exec` requires the guest agent and runs an application. [UTM scripting](https://docs.getutm.app/scripting/scripting/)
- **Unconfirmed:** Parallels documents headless mode and `prlctl`, but the exact unattended behavior, guest login readiness, and GUI-less Windows guest startup for the tested Windows VM/edition combination is not established by the cited docs; verify that exact workflow before adopting it.
- GitHub’s runner image labels and availability may change. The x64-vs-ARM64 distinction above reflects the linked runner documentation; a CI result only represents the architecture label actually selected.
